# TriageIQ: How It Works and Open Gaps

Notes from a walkthrough of the code. Changes made since: the classifier and critic now use `with_structured_output`, the critic now receives the KB context, and KB search now has a 0.5 distance cutoff (see "Resolved" and "Test results" below).

## How it works

A request to the triage endpoint runs a LangGraph workflow (`app/graph/build.py`):

```
classify -> route -> [confidence >= threshold?]
    yes -> retrieve_kb -> draft_reply_node -> critique -> human_review -> END
    no  -> flag_low_confidence -> human_review -> END
```

The graph has one conditional edge, after `route`. The threshold is `low_confidence_threshold` in `app/config.py` (default 0.6); exactly the threshold counts as confident. Low-confidence tickets skip retrieval, drafting and critique, so their response has `suggested_reply: null` and `kb_sources: []`. `triage_ticket` (`app/api/triage.py`) builds the initial state `{"ticket": ticket}`, calls `invoke(...)` on the graph it gets from `get_graph` (built at startup, with `thread_id` = the ticket id), and maps the final state to a `TriageResult`.

`GraphState` (`app/models.py`) is a `TypedDict` with `total=False`, so the state can start with only `ticket`. Each node adds its own fields.

| Node | File | Writes | Notes |
|---|---|---|---|
| `classify` | `graph/classifier.py` | `classification` | LLM, temperature 0, `with_structured_output(ClassificationResult)` |
| `route` | `graph/router.py` | `routing_target` | No LLM. Map lookup by category, plus `-urgent` suffix for high/critical |
| `retrieve_kb` | `graph/kb_retrieval.py` | `kb_context` | Vector search on subject + body: up to 3 matches within 0.65 cosine distance (may be none). `grade_kb` then filters them. Each match is a `KbMatch` (`topic`, `content`, `distance`), and the API returns them as-is in `kb_sources` |
| `draft_reply_node` | `graph/reply_draft.py` | `draft_reply`, `draft_truncated` | LLM, temperature 0.3, grounded in `kb_context`. `draft_truncated` is true when Claude's stop reason was `max_tokens` |
| `flag_low_confidence` | `graph/flag_low_confidence.py` | `needs_human_review`, `review_reason` | No LLM. Runs instead of the three nodes below when confidence is under the threshold |
| `critique` | `graph/critic.py` | `needs_human_review`, `review_reason` | Flags without an LLM call if the KB failed, had no match, or the draft was cut off at the token limit (all applicable reasons are joined). Otherwise an LLM reviews the draft against the ticket, classification and `kb_context` |

| `human_review` | `graph/human_review.py` | `review_decision`, `final_reply` | No LLM. Returns `{}` unless `needs_human_review`. If flagged it calls `interrupt()` with a plain-dict payload (reason, suggested reply, category, urgency, routing target) and waits for a `ReviewDecision` (`approve` / `edit` / `reject`). `final_reply` is the draft on approve, the edited text on edit, `None` on reject (also `None` on approve when there was no draft) |

The node is named `draft_reply_node` because LangGraph does not allow a node name to match a state key (`draft_reply`).

## Knowledge base (`app/kb/`)

The `retrieve_kb` node finds up to 3 KB articles close in meaning to the ticket, using semantic search.

- **Embedding (`store.py: embed_text`).** Text is sent to Voyage AI (`voyage-3`), which returns 1024 numbers. `input_type` is `"document"` when storing articles and `"query"` when searching, because Voyage tunes the embeddings differently for each.
- **Storage.** Articles live in Postgres, table `kb_documents` (`id`, `topic`, `content`, `embedding VECTOR(1024)`), using the `pgvector` extension.
- **Search (`search_similar`).** Keeps articles with `embedding <=> query_embedding < MAX_DISTANCE` (cosine distance, `MAX_DISTANCE = 0.65` since M5.2a, 0.5 before), ordered closest first, `LIMIT 3`. It returns a `list[KbMatch]` (`topic`, `content`, `distance`), which may be shorter than 3 or empty. The drafter and critic see each match as a `- [topic] content` line (`graph/formatting.py`).
- **Seeding (`ingest.py`).** A script, run with `python -m app.kb.ingest`. It is safe to re-run: documents are identified by `topic`, and re-running updates an existing topic's content and embedding in place instead of adding a row. It applies the database migrations, then embeds and saves 5 sample FAQ documents (password reset, billing cycle, account lockout, subscription cancellation, two-factor authentication). It sleeps 20 seconds between documents to stay under the Voyage free-tier limit of 3 requests per minute.
- **Nothing close enough.** If the table is empty or no article is within the cutoff, search returns `[]` and the drafter and critic see "No relevant knowledge base articles found."

## Database layer (`app/db.py`, `app/migrations.py`, `alembic/`)

- **SQLAlchemy 2.0 (sync) with psycopg 3.** `app/db.py` holds the engine, the session factory and `get_session()` (one transaction: commit on success, roll back on error). `DATABASE_URL` is converted from `postgresql://` to `postgresql+psycopg://`, because the plain form would select `psycopg2`, which is not installed. Creating the engine does not connect.
- **ORM models:** `KbDocumentRow` (`app/kb/orm.py`, with pgvector's `Vector(1024)` column) and `TicketRow` (`app/tickets/orm.py`). They are named `...Row` to keep them apart from the Pydantic API models. The stores map rows to the Pydantic models.
- **The schema belongs to Alembic, with one exception.** `alembic/versions/0001_initial_schema.py` is the only place that creates our tables, the `vector` extension and the indexes. It skips anything that already exists and removes duplicate topics (keeping the lowest `id`), so it adopts a database created by the earlier raw-SQL setup. The exception is the LangGraph checkpoint tables (`checkpoints`, `checkpoint_blobs`, `checkpoint_writes`, `checkpoint_migrations`): the `langgraph-checkpoint-postgres` library owns them and creates and upgrades them itself in `PostgresSaver.setup()` (see "Graph startup and checkpointing"). They are deliberately not in our migrations or ORM models.
- **Migrations run at startup:** `main.py` calls `run_migrations()` through the retry wrapper. If the database never comes up the app still boots and logs an error. `python -m app.kb.ingest` also runs them first. Migrations can be run by hand with `alembic upgrade head`, which reads `DATABASE_URL` from the settings.
- **Changing the schema:** edit the model, then `alembic revision --autogenerate -m "..."`, review the generated file, commit it. `alembic check` reports drift between the models and the database.
- **Docker:** the Dockerfile copies `alembic.ini` and `alembic/`, so the container can migrate itself. A guard test checks this.
- **Limits.** Nothing locks migrations, so run one app instance at a time. A failed migration is retried and then ignored, which leaves the app running with missing tables until it is fixed. Every run also writes checkpoint rows (see "Graph startup and checkpointing") and nothing prunes them yet.
- **Tests.** Most tests need no database. The ones in `tests/integration/` run against a real Postgres and are skipped unless `TEST_DATABASE_URL` is set, for example `TEST_DATABASE_URL=postgresql://triageiq:triageiq@localhost:5433/triageiq_test`. The database name must end in `_test`; it is created if missing and wiped before each test. They never use `DATABASE_URL`.
- **Port gotcha.** In `.env`, `DATABASE_URL` points at `localhost:5432`, but the compose database is published on host port `5433`, and `5432` is a different local Postgres. Inside compose the app uses `db:5432` and is unaffected. Commands run from the host need the right port.

## Graph startup and checkpointing (`app/graph/checkpointer.py`, `app/api/deps.py`, `app/main.py`)

- **The graph is built at startup, not at import.** `build_triage_graph(checkpointer=None)` compiles the graph with the given checkpointer. Importing `app.graph.build` no longer touches the database. The startup hook (`main.py`) applies the migrations, then creates the checkpointer, compiles the graph and stores it on `app.state.triage_graph`. On shutdown it closes the connection pool.
- **A Postgres checkpointer.** `create_checkpointer()` opens a `psycopg` connection pool (autocommit and dict rows, which the library requires) and calls `PostgresSaver.setup()` once. If the database cannot be reached it fails after 5 seconds and closes the pool, so nothing is left behind.
- **`thread_id` = `ticket_id`.** `POST /triage` calls the graph with `config={"configurable": {"thread_id": ticket_id}}`, so every run's state is saved under the ticket's id and can be found again by it. This changes no response: the API output is identical to before. It prepares human-in-the-loop review, where a run will pause and later resume under that id. No interrupt or review node exists yet.
- **If startup cannot create the graph** it retries (3 attempts), then logs the error and boots anyway with `app.state.triage_graph = None`. `POST /triage` then returns `503` with `Retry-After`, and `/ready` returns `503` (reason `triage graph unavailable`) even if the database check passes. Restart the app once the database is reachable. `GET /tickets` and `/health` keep working.
- **`get_graph`** (`app/api/deps.py`) is the FastAPI dependency that hands the endpoint the graph. Tests replace it with a graph that uses an in-memory saver, through an autouse fixture in `tests/conftest.py`, so none of them needs Postgres. The real startup and the real checkpointer are covered by tests in `tests/integration/`.
- **Versions.** The AI libraries are on their current stable lines, all pinned exactly in `requirements.txt`: `langgraph 1.2.16`, `langgraph-checkpoint 4.3.0`, `langgraph-checkpoint-postgres 3.2.0`, `langgraph-prebuilt 1.1.1`, `langgraph-sdk 0.4.8`, `langchain-core 1.6.12`, `langchain-anthropic 1.7.6`, `anthropic 1.15.0`, `langsmith 0.14.11`, `psycopg-pool 3.3.3`. The umbrella `langchain` package is no longer installed: nothing imports it (only `langchain_core` and `langchain_anthropic`). Upgrading from the 0.2.x / 0.3.x line needed no change to the pipeline's behaviour: the request bodies sent to Claude were compared before and after and differ only in `max_tokens` (see gap #10).
- **Checkpoint serializer allowlist.** `app/graph/checkpointer.py` passes `JsonPlusSerializer(allowed_msgpack_modules=CHECKPOINT_TYPES)` to the saver. `CHECKPOINT_TYPES` names the app's own types that sit in the graph state (`TicketIn`, `ClassificationResult`, `KbMatch`, `Category`, `Urgency`). Without it the checkpoint library loads them with a "will be blocked in a future version" warning. With it, anything not listed is **blocked and comes back as a plain dict**, with only a log line, so a resumed run would fail with an obscure `AttributeError`. **When you add a type to `GraphState` (or to a model inside it), add it to `CHECKPOINT_TYPES`**; `tests/test_checkpointer.py` walks `GraphState` and fails if one is missing, and the tests' in-memory saver uses the same serializer.
- **Checkpoint tables are upgraded by the library on startup.** The new `langgraph-checkpoint-postgres` takes the checkpoint tables from its migration version 4 to 9 the first time `setup()` runs: one added column (`checkpoint_writes.task_path`, `NOT NULL DEFAULT ''`) and three indexes, nothing removed or changed. Until `setup()` has run, the new library cannot read the old tables at all (`column cw.task_path does not exist`). Checkpoints written by the old libraries, finished and paused, were read back and resumed correctly by the new ones. Rolling back to the old image afterwards should still work (the new column has a default), but that was not tested.
- **Entry point and tracing names.** The graph starts with `add_edge(START, "classify")`, not the older `set_entry_point`. LangSmith tracing uses the `LANGSMITH_TRACING` / `LANGSMITH_API_KEY` / `LANGSMITH_PROJECT` names; the older `LANGCHAIN_*` names still work, but **if both sets are present and disagree, tracing is on when either says true**, so remove the old names from your `.env` instead of adding the new ones beside them.
- **Not done on purpose:** there is no retention policy yet. Every run writes checkpoint rows that nothing deletes.

## Tickets (`app/tickets/`)

Every successful triage is saved, so results can be read back and, later, paused for human review.

- **Table `tickets`** (created by migration 0001, extended by 0002; both run at startup, see "Database layer"): `id` (UUID, primary key), `reference` (text, NOT NULL, unique constraint `tickets_reference_key`), `status`, the original `subject`, `body` and `customer_id`, the triage result (`category`, `urgency`, `confidence`, `routing_target`, `suggested_reply`, `kb_sources` as JSONB, `needs_human_review`, `review_reason`), the review result (`final_reply`, `review_note`, `reviewed_at`, all nullable), and `created_at` / `updated_at`. Index on `(status, created_at)`.
- **Statuses.** `pending_review` when the result is flagged for human review, otherwise `triaged`. After a review: `approved`, `edited` or `rejected`. The column is plain text (no Postgres enum, no CHECK), so adding statuses needed no migration; the allowed values live in `TicketStatus` (`app/models.py`).
- **The reference** (`app/tickets/reference.py`): `TKT-` plus 6 characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (no `0`, `O`, `1`, `I`, `L`), drawn with `secrets`. 31^6 is about 887 million values. It is generated in `app/api/triage.py` next to `ticket_id`, before the graph runs, and is not part of the graph state. `save_ticket` returns the reference it stored: on a collision with the unique constraint it draws a new one and retries up to 3 more times (only for `tickets_reference_key`; any other integrity error, such as a duplicate id, propagates), and `triage.py` puts the returned value in the response so it always matches the row.
- **Migration 0002** adds `reference`, `final_reply`, `review_note` and `reviewed_at`. `reference` is added nullable, every existing row is given a unique one (a copy of the generator is inline in the migration, which imports no app code, and it draws again on a duplicate), then it is set NOT NULL and given the unique constraint. Downgrade drops the constraint and the four columns. A downgrade does **not** change statuses: a ticket already `approved`, `edited` or `rejected` keeps that text, which code from before 0002 would not accept. **The next time the real app starts, 0002 is applied to the real database** (migrations run at startup).
- **Store functions for reviews.** `get_ticket_by_reference(reference)`, and `record_review(session, ticket_id, decision, final_reply)`: one `UPDATE ... WHERE id = :id AND status = 'pending_review' RETURNING ...` that sets the new status, `final_reply`, `review_note`, `reviewed_at` and `updated_at`, and returns the record or `None` (unknown id, or not pending). That single compare-and-set is the database-level guard against two reviewers: whoever updates second matches no row. The caller owns the transaction. `record_review` is called by the review endpoint (see "The review endpoint"), after `resume_review` and inside the same transaction. `get_ticket_for_update(session, ticket_id)` is the locking read the endpoint uses first.
- **The ticket id is created before the graph runs** (`uuid4()` in `app/api/triage.py`) and is the graph run's `thread_id`, so a paused graph run can later be resumed by ticket id. `POST /triage` returns it as `ticket_id`.
- **When rows are saved.** After a successful graph run only, and low-confidence tickets are saved too. If the graph fails, nothing is saved.
- **Endpoints.** `GET /tickets?status=<triaged|pending_review|approved|edited|rejected>&limit=<1-200, default 50>` lists newest first. `GET /tickets/{ticket_id}` returns one ticket, 404 if missing, 422 for a malformed id. `POST /triage` and both GET responses include `reference`; the GET responses also include `final_reply`, `review_note` and `reviewed_at`. Adding `reference` to the `POST /triage` response is an additive API change.
- **A failed save returns 503.** A database that is unreachable (`sqlalchemy.exc.OperationalError`, or the driver's `psycopg.OperationalError` it wraps) gets a 503 with `Retry-After`, the same as LLM outages. Note that the triage work has already been done and paid for when the save fails, and the response is lost with it.
- **Shared database helper:** `app/db.py` (engine, session factory, `get_session`), used by both the KB and ticket stores.

## Human review pause (`app/graph/human_review.py`, `app/graph/review.py`)

- **What happens.** Both paths into the end of the graph go through `human_review`. Unflagged: it writes nothing. Flagged: `interrupt()` pauses the run, and `graph.invoke()` returns the state so far plus an `"__interrupt__"` entry. `POST /triage` builds its response from named keys only, so that entry never reaches the client, and a paused run is saved as `pending_review`. No endpoint, DB column or API contract changed.
- **Resume.** `review.is_paused(graph, ticket_id)` checks `get_state(...).next`. `review.resume_review(graph, ticket_id, ReviewDecision)` raises `ReviewNotPending` (before running anything) for an unknown, finished or already reviewed ticket, otherwise invokes `Command(resume=decision.model_dump())` and returns the final state. Verified on a real PostgresSaver across a simulated restart (new pool, saver and graph).
- **Re-run rule.** On resume LangGraph re-executes the whole `human_review` node. Nothing before `interrupt()` may have side effects. Tests count the `interrupt()` calls (1 at pause, 2 after resume) and check the classify, draft, critic and KB calls are not repeated.
- **The payload and decision are plain dicts**, so the checkpoint serializer allowlist needs no new entry.
- **Known gap: crash between pause and save.** If the app fails after the graph pauses but before `save_ticket`, a paused thread exists with no ticket row, and the client gets a 503. A retry creates a new ticket id, so the orphan thread is never found.
- **Known limitation (LangGraph 1.2.16): a bad raw resume strands the ticket.** If `graph.invoke(Command(resume=<invalid>))` is called directly, the node raises `ValueError("Invalid review decision: ...")` and the ticket stays paused, but the invalid value is saved as the task's pending write and replayed on every later resume, so even a valid decision then fails. Measured on MemorySaver and on PostgresSaver, in the same process and after a restart. `resume_review` avoids this because it only accepts a validated `ReviewDecision`. Pinned by a strict `xfail` test. A possible fix (not done, it changes the "raise a clear ValueError" rule): make the node loop and call `interrupt()` again on invalid input.
- **Other resume quirks seen:** `Command(resume=None)` raises an internal `UnboundLocalError`, and `Command(resume={})` is a silent no-op (the ticket stays paused). A dict whose keys are not interrupt-id digests is treated as one resume value.
- **Two reviewers at once** is now handled and tested, one level up, by the review endpoint's row lock (see "The review endpoint").

## The review endpoint (`app/api/review.py`, `app/api/auth.py`)

`POST /tickets/{ticket_id}/review`, body `ReviewDecision`, response `TicketRecord`.

- **Auth** (`require_review_key`): the `X-API-Key` header is compared with `REVIEW_API_KEY` using `secrets.compare_digest` on bytes. An empty setting means the endpoint is disabled (503, whatever header is sent); a missing or wrong key is 401. The setting is read on every request. The key is checked before anything else, including body validation and the graph lookup, so an unauthenticated caller gets 401 even for a malformed body.
- **The flow**, all inside one `with get_session()` (which commits when the block ends normally and rolls back on any exception, `HTTPException` included): (a) `get_ticket_for_update` reads the row with `SELECT ... FOR UPDATE`, which locks it until the transaction ends; unknown id is 404. (b) status other than `pending_review` is 409. (c) `resume_review(graph, ticket_id, decision)`; `ReviewNotPending` is 409 and `ReviewNotAllowed` is 422. (d) `record_review(...)`, the compare-and-set UPDATE; `None` is 409. (e) return the updated record; the commit happens as the block exits.
- **The lock** makes two simultaneous reviews of one ticket safe: the second request waits at (a), and when the first commits it sees `approved` and answers 409 without touching the graph. The compare-and-set in (d) is a second line of defence. The concurrency tests prove the lock matters: with `with_for_update()` removed, both requests got into `resume_review`.
- **Only a validated `ReviewDecision` is passed to `resume_review`**, because FastAPI validates the body first (422 otherwise). A raw invalid resume value would strand the ticket (see "Human review pause").
- **Approve needs a draft.** `resume_review` raises `ReviewNotAllowed` when the action is `approve` and the paused state has no `draft_reply` (low-confidence tickets skip drafting). Edit and reject work without one. This replaced the M2.7b behaviour where such an approve produced `final_reply = None`.
- **`GET /tickets/reference/{reference}`** lives in the same file. It has two path segments, so `/tickets/{ticket_id}` (one segment) can never capture it. Unknown reference is 404.
- **Known gaps.**
  1. *Graph and row are not one transaction.* If the graph resumes (step c) and the commit (or step d) then fails, the rollback restores the row to `pending_review` but the graph run has already finished and cannot be paused again. The row then says `pending_review` for a run that is no longer paused, and a retry gets 409. Fixing it needs a reconcile step or a different order (record first, resume after), neither of which is built.
  2. *Reads are unauthenticated.* `GET /tickets`, `GET /tickets/{id}` and `GET /tickets/reference/{reference}` need no key and return the customer's subject and body.
  3. *No reviewer identity is recorded.* Only the optional `note` is stored.
  4. *One shared API key,* no rotation, no per-reviewer revocation, no rate limit.
  5. *The lock is held while the graph runs.* Fine at this scale; a slow graph step keeps a row locked and a database connection busy.

## Eval harness (`evals/`)

- **Pieces.** `evals/scoring.py` is pure (no I/O, no LLM): `score_ticket(label, output)` returns one `{result, expected, actual, detail}` per check, and `summarize(scored)` gives pass/fail/skip counts plus the missed-flag and extra-flag ticket ids. `evals/run_eval.py` is the runner.
- **State keys read** (same as `app/api/triage.py`): `classification` (`.category`, `.urgency`, `.confidence`), `routing_target`, `draft_reply` (absent for low-confidence tickets), `kb_context` (list of `KbMatch`, field `topic`, closest first), `needs_human_review`, `review_reason`, plus `draft_truncated` and `kb_failed`. A paused run is `invoke()`'s return value with an extra `"__interrupt__"` key; it is scored from that state.
- **Checks.** Category and urgency compare strings. Urgency is skipped when the label is `null`. The flag check also records `missed_flag` and `extra_flag`. `kb_topic` compares the first source's topic (or `None`). The two phrase checks are skipped with no draft or no phrases.
- **Runner.** One ticket at a time, in dataset order, a fresh uuid thread id each, on a `MemorySaver` (built with the production serializer). An exception is recorded as the ticket's `error` and the run goes on. It checks both API keys (names only, never values) before the first ticket. It never calls `save_ticket`, so nothing is written to `tickets`; the only database use is the KB lookup in `retrieve_kb`. Latency is wall clock per ticket, errors included.
- **Retrieval report (`evals/retrieval_report.py`).** Embeds each ticket the way production does (`f"{subject} {body}"`, voyage-3, `input_type="query"`, through `embed_text` so the rate limiter, retry and cache apply) and runs one read-only SELECT (`SET TRANSACTION READ ONLY`, no WHERE, no LIMIT) for every `kb_documents` row. The query-text f-string is a copy of the one in `kb_retrieval.py`; a test pins the two together. Gap rule: a cutoff `c` (keep distance `< c`) works when `max(correct rank-1 distance) < c <= min(null-ticket top-1 distance)`. Never run against real Voyage or the real database yet.
- **KB articles rewritten (2026-10-21).** The one-sentence articles sat too far from the wording real customers use, which the retrieval distance report is built to show. Each article now has a title, who it is for and a plain-words explanation, 120 to 200 words, with the original policy sentences kept word for word (pinned by `tests/test_kb_articles.py`) and no new facts. Written from the policy alone, without reading the eval set. The database keeps the old text and embeddings until `python -m app.kb.ingest` is re-run (an upsert on `topic`, which replaces both content and embedding). After re-ingesting, re-run the retrieval report to see the new distances; `MAX_DISTANCE` was not changed.
- **KB relevance grader (`app/graph/kb_grader.py`, node `grade_kb`).** Added because two retrieval reports showed the ranking was right 9/9 but no single distance cutoff separated articles that answer a ticket from articles that only share its topic. `MAX_DISTANCE` went from 0.5 to 0.65 (it now only drops clearly unrelated articles) and one structured Claude call keeps the relevant ones. Flow: `retrieve_kb -> grade_kb -> draft_reply_node`. No call when `kb_failed` or `kb_context` is empty. The result is a plain dict in `kb_grade` (`relevant_topics`, `reason`, `status` of `ok`, `rejected` or `unavailable`), so no checkpoint allowlist entry is needed; it is not in any API model. Topics the model returns that were not candidates are ignored, and kept articles stay in retrieval order. With no article left, the ticket takes the same path as "No knowledge base match." (the drafter still runs, with no context; the critic's rule check flags it without an LLM call). The grader sets no review reason itself: `critique` reads `kb_grade.status` and uses "KB article does not answer the ticket." or "KB relevance check unavailable." in place of "No knowledge base match.", because the critic's rule check would otherwise overwrite anything set earlier. Any grader failure (timeout, exception, output that is not the schema) becomes `unavailable`, never an error response. The ticket sits between `TICKET START` and `TICKET END`, and the prompt says it is customer data whose instructions must be ignored; this is a mitigation, not a guarantee, since text such as "TICKET END" inside a ticket is not escaped. Eval note: `kb_sources` in the output (and so the `kb_topic` check) is now the graded list.
- **Injection flag (M5.2b).** The grader's output has `injection_suspected` (default false), stored in `kb_grade` as a plain bool. `critique` checks it FIRST: if true, it returns `needs_human_review: true` with "Possible prompt injection in the ticket." and nothing else, so it overrides the grader's rejected reason, "No knowledge base match." and a truncated-draft reason. Like the other rule checks it returns before the Claude critic call, so that call is skipped. The grader's filtering is unchanged: a relevant article is still kept and drafted from. On `unavailable`, `injection_suspected` is false, which means "not checked", not "checked and clean". Limit: the check lives in the grader, which only runs when there is at least one candidate article, so it does not cover tickets with no candidate, tickets whose retrieval failed, or low-confidence tickets (they skip retrieval). A false negative on those is silent. Detection quality is unmeasured: the prompt has not been run against real injections or against forceful but honest tickets.
- **Stricter grader prompt (M5.2c).** The grader accepted an article that described a related but different situation (same topic, different trigger, cause, feature or account state). The relevance rule now requires the article to explicitly cover the customer's specific situation, says a similar situation that the article does not say applies here is not relevant, and defaults to "not relevant" when unsure. Prompt wording only; no logic or schema change. Risk to watch: the grader may now reject articles that are correct, which costs a human review (reason "KB article does not answer the ticket."). Not measured with real calls.
- **Two KB policy gaps closed (M5.3).** The eval found that the KB did not say whether failed 2FA codes count toward the account lockout (decided: yes, they count as failed login attempts), and that it contradicted itself on refunds for mid-period plan changes (decided: the difference is prorated; the no-partial-refunds rule is for cancelling a subscription only). Three sentences were appended to the end of the account lockout, billing cycle and subscription cancellation articles, word for word, and pinned by `tests/test_kb_articles.py`. These are policy decisions made by the owner, not facts found in the product. The database still holds the old articles and embeddings until `python -m app.kb.ingest` is re-run.
- **Drafter grounding rules (M5.4).** Three repeated eval runs showed three kinds of drafter mistake: advice that is not in the KB, claims about the customer's account that the agent cannot know, and template placeholders left in replies. One of the three slipped past the critic. The drafter's system prompt (`app/graph/reply_draft.py`) now has a "Rules for every reply" paragraph, one rule per mistake: use only facts stated in the articles, never claim to have checked or changed the account, and never leave placeholders. Prompt wording only; the existing instructions are unchanged. Not measured with real calls, so it is unknown how much this reduces the mistakes, and a stricter drafter may say "a member of the team will follow up" more often.
- **Classifier definitions (M5.5).** The eval labels follow written category and urgency definitions. The classifier's system prompt (`app/graph/classifier.py`) now carries the same definitions, appended after its existing instructions, so the labels and the system share one spec. Prompt wording only. Two things to watch: the older sentence ("refunds and charges stay under billing", "shipping for orders that are late, lost, damaged or undelivered") and the new shipping line ("returns and wrong items") overlap without contradicting; and "other" now also means "too vague to tell", which may push more vague tickets to `other` and, with low confidence, to human review. Not measured with real calls.
- **Category "other" goes to a human (M5.6).** `route_by_confidence` (`app/graph/build.py`) now sends a ticket to `flag_low_confidence` when its category is `other` OR its confidence is below `low_confidence_threshold`, so those tickets skip retrieval, grading, drafting and the critic and pause at `human_review`. The node sets "Low classifier confidence." when confidence is below the threshold (including when both apply) and "Ticket could not be categorised." otherwise. No later node overwrites it: `human_review` only reads the reason. `routing_target` is untouched. The graph edges did not change. A deterministic rule, no prompt change. Consequence to watch: every genuine "other" ticket now needs a human, and none gets a draft, so the reviewer's `approve` is refused for them (no draft; see "The review endpoint") and they need `edit` or `reject`.
- **Not verified.** The runner has only been run with fake chains and a fake KB. No real Claude or Voyage call has gone through it. The KB lookup failing is swallowed by `retrieve_kb` (the ticket gets `kb_failed` and a flag), so a database outage shows up in the scorecard as kb_topic failures, not as errors.

## Gaps and things to consider

### 1. Wasted LLM call on low-confidence tickets (RESOLVED)
Previously the reply was drafted before the critic checked confidence, so a low-confidence ticket paid for a draft that was then flagged anyway. Resolved by a conditional edge after `route`: tickets under the threshold go to `flag_low_confidence` and make no KB, draft or critic calls.

### 2. `.get()` fallbacks in `triage_ticket` cannot trigger
The graph is linear and every path sets `routing_target`, `kb_context`, `draft_reply`, `needs_human_review` and `review_reason`. The defaults (`"general-queue"`, `[]`, `True`, ...) are harmless but would hide a bug if a node stopped writing a field. Consider `final_state["..."]` so a missing field fails loudly.

### 3. Nodes return the full state
Each node returns `{**state, "key": value}`. LangGraph only needs the changed keys, so `{"key": value}` is enough. The spread can cause update conflicts if parallel branches are added later (for example, running `route` and `retrieve_kb` in parallel).

### 4. Sequential LLM latency
A request makes up to three sequential LLM calls (classify, draft, critique), so per-request latency adds up. The blocking `invoke` is not a problem: the endpoint is a plain `def`, which FastAPI runs in a threadpool.

### 5. Model ID (RESOLVED)
The model is the setting `model_id` (`MODEL_ID`, default `claude-sonnet-4-6`) in `app/config.py`, read by all three LLM calls, so it is defined in one place. Confirm `claude-sonnet-4-6` is the model you intend to run.

### 6. Prompt injection
Ticket text goes straight into the classifier, drafter and critic prompts, and the draft is fed to the critic. A hostile ticket could try to steer the classification or the review verdict. The human-review flag helps, but the critic is itself an LLM reading attacker-influenced text.

### 7. Critic `reason` can be empty
`CritiqueResult.reason` is an empty string when no review is needed. `triage_ticket` handles that with `review_reason or None`. The low-confidence shortcut uses a fixed string, `"Low classifier confidence."`.

### 8. Knowledge base gaps
- **Voyage rate limit at request time.** `ingest.py` sleeps 20 seconds between documents because of a 3 requests-per-minute free-tier limit. But every triage request also makes one Voyage embedding call in `search_similar`. On the free tier, the endpoint would hit the limit after about 3 requests in a minute. Not tested; this follows from the limit stated in the `ingest.py` comment.
- **`topic` is never returned (RESOLVED).** `search_similar` now selects `topic`, `content` and the cosine distance and returns `KbMatch` objects, so the drafter, the critic and the API's `kb_sources` can all show which article a snippet came from. `kb_sources` changed from a list of strings to a list of `{topic, content, distance}` objects.
- **New database connection on every call (RESOLVED).** The raw `get_connection()` is gone. The stores use a SQLAlchemy engine, which pools connections (`pool_pre_ping` enabled), and `CREATE EXTENSION vector` now runs once, in the migration.
- **Ingest is not idempotent (RESOLVED).** `kb_documents` had no unique constraint on `topic`, so running `python -m app.kb.ingest` twice inserted every document twice. Now the initial Alembic migration deletes existing duplicates (keeping the lowest `id` per topic) and creates a unique index on `topic`, and `add_document` is an upsert (`ON CONFLICT (topic) DO UPDATE` content and embedding). The migration is safe on a database that already has the tables, so an existing database with duplicates is cleaned up the first time it runs.
- **Extra latency.** Each retrieval is a Voyage API call plus a Postgres query, even though no LLM is involved.
- **Missing keys fail late.** `voyage_api_key` and `database_url` come from `app/config.py`, where every setting has a default (the API keys default to empty strings). A missing key does not stop the app from starting; it fails at the first Voyage call.
- **The table is not created at startup (RESOLVED).** The app now applies the Alembic migrations at startup with retry (`app/main.py`, `app/migrations.py`, `app/kb/bootstrap.py`), so a fresh database gets its tables without running the ingest script. If the database never comes up, the app still boots and KB lookups degrade to a human-review flag.
- **The cutoff rests on a small sample.** Verified end to end, but only two real-match samples back it. See "Resolved" below.

### 9. Not yet checked
- Error handling: if any node or LLM call raises, `invoke` raises and the endpoint returns a 500. There are no retries or fallbacks.
- Whether the endpoint should return 200 or 201 depends on whether a triage record is persisted. Currently it only computes a result, so 200 is correct.

### 10. Replies longer than the token cap are cut off (MITIGATED: flagged, not prevented)
Every Claude call (classifier, drafter, critic) sends an explicit `max_tokens` from the setting `llm_max_tokens` (`LLM_MAX_TOKENS`, default 700, about 500 words, must be greater than 0). It is set explicitly because `langchain-anthropic`'s own default differs between versions: 1024 in 0.2.x, and the model's maximum (128000 for `claude-sonnet-4-6`) in 1.x. Without a pinned value, upgrading the library would have silently removed the cap. The request bodies were compared on both library versions and only this field differed. 700 is lower than the earlier effective 1024, a deliberate choice.

**What happens when a call hits the cap.**
- **Drafter (the case that used to be silent).** The reply stops mid-sentence. Claude's stop reason is `max_tokens`, and `draft_reply` now keeps it instead of discarding it with the parser: it returns `draft_truncated: true` next to `draft_reply`, and logs a warning with the token count (a finished draft logs an info line with its token count). The critic has a rule-based check for `draft_truncated`: it flags the ticket for human review with the reason "Draft reply was cut off at the token limit." and does not spend an LLM call. The cut-off text is still returned as `suggested_reply`, so a reviewer can see it. If the KB also failed or had no match, the reasons are joined.
- **Classifier and critic.** A cut-off structured answer is missing required fields, so the output parser raises a validation error and the request becomes a `500` (LangChain also logs "Output parser received a `max_tokens` stop reason"). This is loud, not silent, and unlikely at these output sizes, since the structured results are far smaller than the cap. It is not handled specially.

**Verified** on both library versions (0.2.3 and 1.7.6) with the real chains against a fake local Anthropic server that reports `max_tokens`: the ticket is flagged and only the drafter's request is sent. **Not done:** nothing makes cut-offs rarer, and how often they happen on real tickets is unknown. Once real tickets have run, the logged token counts show whether to raise the cap (possibly for the drafter alone) or ask the drafter prompt for shorter replies.

## Resolved

### Critic could not see the KB
The critic's prompt told it to flag claims "not supported by the knowledge base context", but `critique` never passed it the KB articles. It could not verify anything, so it flagged replies that were fully supported by the KB. Fixed in `app/graph/critic.py`: `kb_context` is now formatted (same fallback text as `draft_reply.py`) and included in the critic's prompt.

### KB search returned irrelevant articles (similarity cutoff)
Search used to return the top 3 articles regardless of relevance, so a password question also got lockout and 2FA paragraphs, and a hardware refund question got 3 unrelated articles. Fixed in `app/kb/store.py` with `MAX_DISTANCE = 0.5`. The value came from measuring cosine distances (read-only script, 5 Voyage calls) from 5 test queries to the 5 sample articles:

| Query | Closest article | Distance | 2nd closest |
|---|---|---|---|
| Password reset (real match) | password reset | 0.332 | 0.565 (lockout) |
| Cancel subscription (real match) | subscription cancellation | 0.351 | 0.652 |
| Charged twice (partly related) | billing cycle | 0.642 | 0.747 |
| Hardware refund (irrelevant) | account lockout | 0.735 | 0.771 |
| Weather in Paris (unrelated) | account lockout | 0.817 | 0.833 |

Real matches landed at about 0.33-0.35 and everything else at 0.565 or higher, so 0.5 sits inside the gap.

**Status: verified end-to-end (2026-10-05).** After rebuilding the stack, the lockout ticket returned one matching article in `kb_sources` and a grounded reply that the critic cleared. The shipping ticket returned `kb_sources: []`, a reply that invented no policy, and `needs_human_review: true`. The 0.5 value still rests on only two real-match samples, so retune it when the KB grows or if real tickets with longer bodies score between 0.4 and 0.5. If it is too strict, the result is empty context and a human-review flag, which is the safe direction.

The blocking-invoke concern formerly listed as gap #4 is therefore a non-issue for the current code. It would only apply if someone changed this to async def without switching to ainvoke. The note has been corrected.

## Gateway foundation (M3.1)

- **Same repo.** The gateway lives in `gateway/` next to the Python service, not in its own repository. One `docker compose` file runs both, and one commit can change both sides of a contract.
- **ioredis.** BullMQ (the planned queue in M3.2) is built on ioredis, so the gateway uses the same client library from the start instead of adding a second Redis client later. One client is provided through Nest DI. It connects in the background and retries, so the app boots with Redis down; its error handler logs only an error code, never the URL.
- **Python stays reachable (closed in M3.5b).** Port 8000 was published (later bound to `127.0.0.1`); M3.5b removed the mapping, so only the gateway can call the Python service. That only changes at M3.5, once the gateway has auth and rate limits. Until then the gateway adds no protection.
- **Config.** `@nestjs/config` with a zod schema. The error message is built from the setting NAME and a fixed hint, never the value, so a password in `REDIS_URL` cannot reach a log. A first version used `new URL()` inside a zod refine and leaked the input in a raw TypeError; a test caught it, and the parse is now wrapped so no raw error can escape.
- **Tooling is the Nest 12 scaffold's:** Vitest, oxlint, ESM, TypeScript 6 (TypeScript 7 exists, but the scaffold pins 6, and ts-jest, the usual Jest TypeScript transformer, only supports versions below 7; I did not test Vitest or oxlint on 7). The scaffold's `@nestjs/observe`, `@nestjs/mau`, `nest deploy` script and generated agent docs were removed on purpose.
- **Node 24.** The Dockerfile uses `node:24-slim`, and the tests were run inside a `node:24` container so the tested Node matches the runtime Node.
- **/ready shape.** A failing check is `"down"` in `checks`, and a sibling `reasons` object holds the short reason. The top-level status is `not_ready` (the Python service uses the same word). Only the status code of the Python `/ready` is used.
- **Redis is published on 6380 with no password**, the same way Postgres is published on 5433. Every published port in the compose file is bound to `127.0.0.1` (Postgres 5433, Redis 6380, the gateway 3000), so none is reachable from other machines. The Python app's port is not published at all since M3.5b.

## Ticket intake on the gateway (M3.2)

- **BullMQ** (`bullmq` 6.7.8 with `@nestjs/bullmq` 12.0.2), one queue named `triage`, connected with `REDIS_URL`. BullMQ was the reason for ioredis in M3.1. The queue has its own connection, separate from the client used by `/ready`. No Worker exists yet; jobs stay queued until M3.3.
- **The gateway makes the job id** (`crypto.randomUUID()`), not BullMQ. The client gets a stable id that does not depend on Redis counters, and later steps can use the same id as an idempotency key.
- **400 for validation**, not 422, with `{field, problem}` entries. Messages are built from the field name and a fixed phrase, never the value. Unknown field names are echoed, cut to 50 characters.
- **Stricter than the Python `TicketIn`** on purpose (length limits, no empty subject or body, no `null` customer_id). A ticket the gateway accepts is always valid for Python, not the other way round.
- **Retention:** completed jobs are removed after 1 day, failed jobs after 7 days (changed to 30 days in M3.4a). Jobs that are still queued are kept until processed.
- **2 second deadline** on every queue call. A bug found by testing against a real Redis: with Redis down, BullMQ keeps the `add` call pending, so the client got a 503 and the ticket was stored anyway when Redis came back (a retry would then duplicate it). The fix: wait for the connection to be ready first, and skip the write if the deadline has already passed. After the fix, a 503 means nothing was stored, in both cases tried (Redis down at request time; Redis dropping after the gateway had connected). The queue connection also has `enableOfflineQueue: false`, so a mid-run drop fails at once instead of waiting. Not covered: Redis that is slow rather than down, where an `add` that takes longer than 2 seconds still completes later.
- **Body limit** is set in `app.setup.ts` (shared by `main.ts` and the tests): Nest's default parser is turned off (`bodyParser: false`), the JSON parser is added with `limit: '100kb'`, and an error handler right after it turns parser errors into JSON (413, 400, 415). Without it Express would send an HTML error, and the text for bad JSON can quote the input.
- **Unmapped job state:** `GET /jobs/:id` maps every BullMQ state, except that BullMQ's `unknown` (the job vanished between two reads) gives 404 and any future unrecognised state gives 500, logged.
- **The honest gap:** between intake and the moment the Python service saves the ticket, a ticket exists only in Redis. Redis persistence is on (appendonly), but it is a single instance with no replica and no backup, and appendonly with the default fsync setting can lose about a second of writes on a crash. Until the worker exists nothing ever reaches Postgres. Also open: no idempotency (a client that retries after a timeout can create a duplicate), no auth, no rate limit, no retries or dead-letter handling.

## The triage worker (M3.3)

- **Inside the gateway process.** One `@nestjs/bullmq` processor in `src/worker/`, started with the app. One process to deploy for now. The cost is that intake and processing share a process and a restart interrupts both; it can be split out later because the queue is the only thing they share.
- **Retry rules.** Retry only when waiting can help: 503 and 429 (the service says "later", and `Retry-After` is honoured), 502/504 and network failures (timeout, refused, DNS, reset). Everything else fails at once. **500 and every other 5xx are not retried on purpose:** Python returns 500 for problems no retry fixes (an invalid API key, a bug), and each retry repeats paid LLM calls. 2xx with a body that is not JSON also fails at once. An error from `fetch` that is not a recognised network failure fails at once, because that is more likely a bug on our side than something a retry fixes. The cost: a transient failure with an error code not in the list (see `triage-outcome.ts`) fails a ticket that a retry would have saved.
- **BullMQ APIs used (attempts raised to 8 in M3.4a):** `attempts: 5` and `backoff: { type: 'custom' }` in the queue's `defaultJobOptions`; `settings.backoffStrategy` on the worker (signature `(attemptsMade, type, err, job)`), which reads `retryAfterSeconds` off the error the processor threw (`RetryableTriageError`); `UnrecoverableError` to fail a job at once. A test checks that a `Retry-After: 20` really produces a 20 s delay, not the 10 s base.
- **Backoff:** `max(Retry-After, 10 s x 2^(n-1))` after attempt n, capped at 5 minutes. With 5 attempts only 10, 20, 40 and 80 s are ever used; the cap and the longer steps only matter if attempts are raised.
- **Concurrency** (`WORKER_CONCURRENCY`, default 2) protects the Claude and Voyage rate limits as much as the Python service: each ticket is several LLM calls plus an embedding. Voyage's free tier allows 3 requests per minute and the Python service waits for it, so a request can legitimately take a long time; that is why `TRIAGE_TIMEOUT_MS` defaults to 2 minutes. `@nestjs/bullmq` fixes worker options when the code loads, so concurrency is set on the finished worker (`worker.concurrency`) from config.
- **Failure reasons** are fixed phrases (no URL, stack, response body or ticket text) because they are stored on the job and returned by `GET /jobs/:id`. The worker logs job id, attempt, outcome and duration, never ticket text.

Bugs found by testing against a real Redis while building this (all fixed, each now has a test):

- **Stale read in `GET /jobs/:id` (from M3.2).** The job was read, then its state was asked for in a second call. A job that finished between the two calls came back as `done` with `result: null`. The job is now read again once its state is `completed` or `failed`.
- **`app.close()` hangs when Redis is unreachable.** BullMQ's `Worker.close()` (and `close(true)`) never returns if the connection never came up, so the whole app hung on shutdown. `ShutdownSafeWorker` (`src/worker/shutdown-safe-worker.ts`, installed through `BullModule.workerClass`) drops the connections instead, but only when the connection is positively seen to be not ready. A first version got this check wrong (in BullMQ 6, `worker.client` is `undefined`, so it always took the hard path) and abandoned running jobs on every shutdown. The shutdown test, which closes the app while a job is running, fails with that bug and passes now.
- **The gateway container ignored `docker stop` (since M3.1).** Nest's shutdown hooks close the app and then send the signal to the process again. In a container node is PID 1, and PID 1 ignores a signal it sends itself, so `docker stop` waited out its whole timeout and killed the process (exit 137). `main.ts` now closes the app on SIGTERM/SIGINT and exits explicitly (an idle gateway stops in under a second with exit 0).

What happens to a running job when the container stops (measured with a 20 s fake triage server): with a stop timeout long enough, the gateway waits for the job, marks it done, and exits 0. With Docker's default 10 s the container is killed with the job still active; BullMQ's stalled-job check finds it after the lock expires (about 60 to 90 s later, once a gateway is running again) and runs it again without using up an attempt. The Python service then receives the ticket twice, and if it had already saved the first one that is a duplicate ticket. BullMQ's default is to fail a job that stalls a second time ("stalled more than allowable limit"); that part I did not test. Later applied by the owner: `stop_grace_period: 130s` on the gateway service in `docker-compose.yml`.

**The honest gap (M3.4b fixes it with idempotency):** if the worker stops after Python has saved the ticket but before the job is marked done, the retry creates a second ticket. This covers a crash, a kill after the grace period, a stall, and a timeout that fires just after Python finished (the timeout abandons the request, not Python's work). Nothing in Python tells the gateway "I already have this one".

## Dead letters and a longer retry window (M3.4a)

- **The failed set is the dead-letter list.** BullMQ already keeps final failures in its failed set, in order of failure, with the job's data and reason. A separate store (another queue or a Postgres table) would need to be kept in step with it and would add a second place for ticket text. Confirmed in the BullMQ 6.7.8 source: a job moves to `failed` only when `shouldRetryJob` says no (attempts used up, or `UnrecoverableError`); a job that will be retried goes to `delayed`. The worker's `failed` event fires on **every** failed attempt, including retried ones, so the dead-letter log line first checks that the job's state really is `failed`.
- **Same job id on retry.** `Job.retry('failed', ...)` moves the job in place (one Lua script that also checks it is in the failed set), so clients keep polling one `status_url` and a double retry cannot create a second copy: the second call finds the job no longer failed and gets 409. A new job with a new id would have been simpler to reason about for the worker but would have broken the link between the ticket the client knows and the one that runs.
- **BullMQ's retry does NOT reset `attemptsMade` by default.** Without options a job that used all its attempts would fail again after one more try. The gateway passes `resetAttemptsMade: true` and `resetAttemptsStarted: true`. Mutation-tested: with both `false`, the retry integration tests fail (a retried job got 1 more try instead of a full set). A retried job gets the attempts it was created with (`opts.attempts`): 8 for jobs created from M3.4a on, 5 for older ones, 1 for jobs created before attempts existed.
- **8 attempts** wait 10, 20, 40, 80, 160, 300, 300 s: 910 s, about 15 minutes. The formula and cap are unchanged. The first backoff step travels with the job (`backoff: { type: 'custom', delay: 10000 }`; the strategy reads `job.opts.backoff.delay`, falling back to 10 s for older jobs). Tests replace the retry policy through the `TRIAGE_RETRY_POLICY` injection token (3 attempts, 50 ms); it is deliberately not an environment setting.
- **30-day retention** for failed jobs. Jobs already in Redis keep the options they were added with (7 days, 5 attempts).
- **No authentication yet.** `GET /dead-letters` and `POST /dead-letters/:id/retry` have no login until M3.5 and the list returns ticket subject, body and customer id. (M3.5a has since added keys and roles, see below.) The gateway port is published on `127.0.0.1` only (`127.0.0.1:3000:3000`); the Python app's port is not published (M3.5b).
- **Limits:** `offset` pagination over a set that changes (a job failing or being retried between two pages can shift items, so a page may skip or repeat one). The retry is not rate limited, and nothing stops someone retrying a job whose cause is not fixed (it just fails again, after another 15 minutes of attempts and paid calls). A retry does not duplicate the ticket in Python if the first attempt had been saved there: that is M3.4b.

## Idempotency end to end (M3.4b)

What was found first (LangGraph 1.2.16, measured with the real graph and faked model calls):

- **`invoke()` with new input on an existing thread always starts a new run from the first node**, whatever the thread holds: after a finished run, after a run paused at `human_review`, and after a run that stopped halfway (the failed node's pending task is not resumed). Every node ran again, so every Claude and Voyage call was repeated. Only `Command(resume=...)` continues a paused run. This is why a repeated `POST /triage` could not simply call `invoke()` again.
- A finished run has `get_state().next == ()` and all its result keys. A paused one has `next == ('human_review',)`. A run that stopped halfway has the failed node in `next`.
- `delete_thread(thread_id)` exists on `PostgresSaver` (and `MemorySaver`) in langgraph-checkpoint-postgres 3.2.0 / langgraph-checkpoint 4.3.0 and removes the thread's checkpoints, blobs and writes. No other way to clear a thread was needed.
- **A primary key collision on save was a 500** (`save_ticket` only retries the `reference` constraint; a test pins that a duplicate id raises `IntegrityError`). That behaviour of `save_ticket` is unchanged; the endpoint now catches it for requests that carry an id.

Decisions:

- **Python decides, not the gateway.** The gateway cannot know whether Python saved a ticket, so the worker sends its job id as `ticket_id` and Python makes the hop idempotent. The job id is the same on every attempt and on a dead-letter retry. A job id that is not a UUID is not sent (all gateway ids are UUIDs).
- **Advisory lock, not a transaction.** `pg_advisory_lock(hashtextextended('triageiq:ticket:' || id, 0))` on its own AUTOCOMMIT connection, held for the whole request (a graph run can take minutes, and an open transaction for that long is worse). Postgres releases it if the connection dies. `lock_timeout` is 150 s (above the gateway's 120 s triage timeout) so a stuck holder produces a retryable 503 instead of hanging the waiting request forever, and the setting is reset before the connection goes back to the pool. Cost: a waiting request holds one of the app's worker threads. Many duplicates of one slow ticket could use up the thread pool.
- **Rebuild from the checkpoint instead of re-running.** If the row is missing but the run finished or paused, the answer is built from the saved state with the same code as a fresh run. It saves model calls and, for a paused ticket, keeps the one thread a reviewer needs. A run that stopped halfway is cleared and run again, because resuming it from outside is not something this app supports.
- **The row wins.** A repeated request returns the stored triage and never compares the text. The gateway always repeats the same ticket under the same id; a different client reusing an id would get the first ticket's answer.
- **Gateway keys in Redis, 24 h TTL.** `SET idem:<key> {job_id, fingerprint} NX EX 86400` is the atomic claim; the ticket is then queued under that job id. Redis already holds the queue, so there is no new dependency, and 24 hours is as long as completed jobs are kept. On a failed or timed-out enqueue the key is deleted only if it still holds this job id (a small Lua `GET`/`cjson.decode`/`DEL`, one step inside Redis), so a key another request has since claimed is never deleted. Mutation-tested against real Redis: with a plain `DEL`, or `SET` without `NX`, the tests fail.
- **A dedicated ioredis connection for the keys**, not the BullMQ queue's. BullMQ 6 has no public `queue.client` (the first version of this code used it and failed against a real Redis: every keyed request was a 503; the fakes had hidden it). The connection has `enableOfflineQueue: false`, so a command sent while Redis is down fails at once and can never be written late, after the client was told 503.
- **Fingerprint** = SHA-256 of `JSON.stringify([subject, body, customer_id ?? null])` after the schema's trimming.

Honest gaps:

- **Keys are not scoped per client** until auth exists (M3.5). Two clients with the same key share it.
- **A key lost from Redis before the job is persisted** (a flush, or a crash within the append-only fsync window) allows a second job for a retry. The Python hop still keeps one ticket per job.
- **A replay that overlaps a failed first attempt** (five concurrent requests, and the enqueue of the one that claimed the key fails) can be told a job id that was never stored. Polling it gives 404; the retry with the same key then works because the key was released. If releasing the key fails too (Redis went down between the claim and the enqueue), the key stays until its 24 h TTL and replays return that missing id.
- **A slow, not down, Redis** can still finish an enqueue after the client was told 503 (as in M3.2); the key is then released and a retry makes a second job.
- **A replayed `202` always says `queued`**, even if the job is done by then. The state is read from `status_url`.
- **The Python lock does not protect the review endpoint** (it has its own row lock), and checkpoints still pile up with no retention policy.
- Concurrency was tested with threads in one process against a real Postgres; two separate app instances would use the same advisory lock but that was not tested.

## Client API keys, roles and rate limits (M3.5a)

Decisions:

- **A registry in an env file, hashes only.** `GATEWAY_CLIENTS` is a JSON array of `{name, role, key_sha256}`. The gateway never stores or logs a key; a leaked `gateway/.env` or process listing exposes hashes of 256-bit random keys, which cannot be reversed. Keys are `tiq_` plus 32 random bytes, so a fast hash (SHA-256) is enough: there is no password to guess, which is where a slow hash such as bcrypt earns its cost. Validation messages carry the setting name and, at most, an entry position, never a name or a hash.
- **`gateway/.env` for the secrets (owner's decision).** The root `.env.example` is pinned by Python tests (every name must be a Python setting), and the root `.env` goes into the Python container wholesale. A separate `gateway/.env`, loaded by compose `env_file`, keeps the hashes out of the Python app's environment. Compose's own message for a missing file cannot be customised, so the pointer to `gateway/.env.example` is a comment in the compose file and the README. `gateway/.dockerignore` already excludes `.env`, so the file is not baked into the image.
- **Constant-time lookup.** The presented key is hashed and compared with every registered hash using `crypto.timingSafeEqual`, without stopping at the first match, so response time does not show whether or how much a hash matched. A unit test checks that every entry is read even after an early match.
- **Three global guards, in this order: authenticate (401), rate limit (429), roles (403).** Public routes (`@Public()`) skip all three. A 401 is never counted. A 403 is counted and carries the rate-limit headers, so a client cannot probe forbidden routes for free. A route with no `@Roles` is open to every authenticated client: a new route is protected by default, but not role-restricted.
- **404, not 403, for another client's job.** A 403 would confirm the id exists. A submitter gets the identical 404 for a foreign job, a missing job, and a job with no `client` (created before M3.5a). The check runs before the job's state is looked at, so even an odd state cannot make the answers differ. Reviewers read any job.
- **`req.apiClient`, not `req.client`:** Node's `IncomingMessage.client` is the socket (deprecated alias), so that name was taken.
- **Per-client idempotency:** the Redis key is `idem:<client>:<key>`. Client names cannot contain `:`, so no two (client, key) pairs share a key. Old `idem:<key>` entries are never read again and expire within 24 hours.
- **Fixed-window limit counted in Redis.** One Lua script (`INCR`, and `EXPIRE` on the first request of a window) so the count and its expiry are atomic and a counter can never be left without an expiry. `Retry-After` is the counter's remaining TTL, so it needs no clock agreement between the gateway and Redis. The window is a test-only injection token (`RATE_LIMIT_WINDOW_SECONDS`, default 60), not a setting. Fixed windows allow a burst of up to twice the limit across a window boundary; a sliding window would not, at the cost of more state and a bigger script.
- **The limiter shares the idempotency Redis connection** (offline queue off, so a command is never sent late). If it cannot answer within the usual deadline the request gets a 503, so with Redis down even `POST /tickets` answers with the limiter's 503 text, not the intake one.
- **No per-IP limit, on purpose.** Behind a proxy or compose network every request would appear to come from one address (or the client could spoof `X-Forwarded-For`), so a per-IP limit would either punish everyone together or protect nothing. Every route except the two health routes needs a key, so an unauthenticated flood only costs the guard's SHA-256 and a 401, and cannot reach Redis or the queue. Limiting that flood belongs to a reverse proxy or firewall in front.
- **helmet 8.3.0 with its defaults.** It also removes `X-Powered-By` (it is applied first, so 401s, 413s and parser errors carry the headers too). Several defaults (CSP, `X-Frame-Options`) matter little for a JSON API but do no harm. `Cache-Control: no-store` was not added.
- **The key tool is a TypeScript file run by Node's own type stripping** (`node scripts/make-client-key.ts`, Node 24), importing `src/auth/client-key.ts` which uses only Node modules and erasable syntax. No new dependency and no build step. It is excluded from the main tsconfig because it imports a `.ts` path.

Remaining gaps:

- **No per-IP limit** (above), and the limit is per client, so one leaked key can use that client's whole allowance.
- **No key rotation tooling** beyond replacing the entry (and recreating the gateway); there is no overlap period where two keys work for one client unless you register two clients.
- **Registry changes need a restart** (read once at startup).
- **Reviewer identity is not passed to Python.** The Python review endpoint still takes one shared `X-API-Key`, and the gateway does not call it yet, so reviews are not attributed to a person. M3.5b.
- **Python reachability** was closed in M3.5b (see below): no published port, so nothing outside the compose network reaches it.
- **Fixed-window burst** of up to twice the limit at a window edge.
- **Key hashes appear in the output of `docker compose config`** and in the container's environment (`docker inspect`), since the registry is an environment variable. They are hashes, not keys.
- **A leaked key is valid until its entry is removed;** there is no expiry.
- **Reviewers see all ticket text** through `GET /dead-letters` and `GET /jobs/:id`.
- **Roles are checked per route by a decorator.** A new route without `@Roles` is open to every authenticated client, including submitters.

## The gateway is the only way in (M3.5b)

- **Python's port is no longer published.** The `app` service has no `ports`; the gateway reaches it at `app:8000` on the compose network. `docker-compose.debug.yml` adds `127.0.0.1:8000:8000` back for local work (`docker compose -f docker-compose.yml -f docker-compose.debug.yml up -d`); compose appends the list, so the base file stays closed. Other containers on the network (the database, Redis) can still reach `app:8000`, and so could anything else added to that network. Nothing was found that needs the host port: the eval harness runs the graph in-process (`MemorySaver`), the retrieval report uses the database directly, and the Python tests use `TestClient` or fakes. Only README examples assumed `localhost:8000`; they now say they need the debug override.
- **A fresh request per call, never the client's headers.** `TriageClient` builds the Python request from scratch: its input is a validated path, query and body, so there is no code path that could copy `Authorization`, cookies or `X-Forwarded-For`. The one credential Python receives is `TRIAGE_REVIEW_API_KEY`. It is sent on reads too (Python ignores it there), so a future key check on reads needs no gateway change. `redirect: 'manual'` stops a redirect from carrying the key to another host.
- **Validate before forwarding.** Ids, references, the list query and the review body are checked in the gateway (same rules as Python: `TKT-` references use Python's alphabet; `edit` needs a non-blank reply). Unknown query parameters are dropped and unknown body fields rejected, so Python only ever sees fields the gateway understands. Bad input never reaches Python, so it cannot spend a database call or leak a FastAPI validation error.
- **502 versus 503.** 502 means the gateway or Python is broken and retrying will not help until someone fixes it: the review key is wrong or unset (Python 401, or its 503 "Review is disabled"), Python crashed (5xx), or it answered something unreadable. 503 means try again later: no connection, a timeout, or Python's own retryable 503 (database or Claude trouble). **Deviation from the task text:** a Python 503 that is not the key check is returned as 503, not 502, because Python marks it as retryable (it sends `Retry-After`); the key-check 503 is told apart by its "Review is disabled" detail, which is an assumption about Python's wording (a test pins it).
- **Only the five statuses worth showing are passed through** (2xx, 400, 404, 409, 422). Everything else, including redirects and 403/405/429, becomes 502, so an unexpected Python answer never reaches the client.
- **Timeouts:** 10 s for reads, 30 s for a review (a review resumes the graph and may run the critic's work again). A test-only injection token lets tests shorten them.
- **`@Res()` instead of a returned value:** Nest overrides a status set on a passthrough response with the route's default (201 for POST), so the controller sends Python's status and body itself.
- **Reviewer role only** (class-level `@Roles('reviewer')`), because these routes return ticket text and can decide a ticket. They share the `/tickets` prefix with intake in a second controller; the paths do not overlap, and the reference route is declared before `:id`.

Remaining gaps:

- **Review decisions do not record which reviewer made them.** Python sees one shared key. Per-person attribution needs user login (M4).
- **Anything on the compose network can still call Python without a key** (only reviews need one). A second service added to the network, or a compromised container, reaches it.
- **One review key for every reviewer client.** Rotating it means changing both `.env` files and recreating the app and the gateway.
- **Python's 422 body is passed through,** and FastAPI's validation errors can echo the submitted input. The gateway validates first, so this should be unreachable.
- **`Retry-After` from Python's 503 is not passed on.**

## M3 in one page: the gateway, end to end (M3.1 to M3.6)

What M3 added, in the order it was built:

- **M3.1 foundation:** a NestJS 12 service (`gateway/`, Node 24, Vitest, oxlint) with validated config, Redis, `/health` and `/ready`.
- **M3.2 intake:** `POST /tickets` validates a ticket and queues it on BullMQ; `GET /jobs/:id` reports its state. 202 means "stored".
- **M3.3 worker:** it sends each job to Python with a retry policy (503, 429, 502, 504 and network failures retry; other 4xx and 500 do not), custom backoff honouring `Retry-After`, and a shutdown that waits for running jobs.
- **M3.4a dead letters:** 8 attempts (about 15 minutes), failed jobs kept 30 days and listed and retried by reviewers, with the same job id.
- **M3.4b idempotency:** `Idempotency-Key` on the gateway (client to gateway), and the job id as `ticket_id` on Python (gateway to Python), so a ticket is queued and saved once however often anything is retried.
- **M3.5a client auth:** hashed API keys, `submitter` and `reviewer` roles, job ownership (404, not 403), per-client idempotency keys and rate limits, helmet.
- **M3.5b only way in:** reviewer routes that forward to Python with the gateway's own review key, and Python's port no longer published (`docker-compose.debug.yml` brings it back for debugging).
- **M3.6 smoke test and docs:** `scripts/e2e_smoke.py` (standard library only) drives the running system through the gateway in nine steps, and the README gained the whole-system diagram, "Life of a ticket", a one-page run guide, a security table, troubleshooting and known gaps.

Decisions that shaped the smoke test:

- **It goes through the gateway only,** with real keys, the way a client would; it imports nothing from `app/` or `gateway/`. It cannot be a unit test of the system, so its own tests (`tests/test_e2e_smoke.py`) run it against an in-process fake gateway: they check the script's logic (steps, dependants skipped on failure, exit codes, no key ever printed), not the real system.
- **It never asserts model wording.** The answerable ticket is checked only for a finished job with a ticket id and a reference in the right format. The one model-dependent check is the vague ticket ("Help" / "It does not work."): category `other` always goes to a human, so it must be flagged. If the classifier ever stopped returning `other` for that text, step 7 would fail even though nothing is broken; that is the only brittle assumption, and it is visible in the report.
- **Test tickets are marked** (`[e2e <run id>]`, customer `e2e-smoke`) and are not cleaned up: there is no delete endpoint. They are real rows in the real database.
- **It was written but not run against a real stack by the author** (the owner runs it, since it spends model calls). Until it has been run once, treat the real-system behaviour it asserts as unverified.

What is still open after M3 (also in the README's "Known gaps"): no reviewer identity until login (M4); no per-IP limit (needed before a public form); one shared review key; a single Redis; a fixed-window rate limit that allows a burst at a window edge; registry changes need a restart; anything on the compose network can call Python without a key.

## Reviewer accounts foundation (M4.1a)

What was built: a gateway-owned Postgres database and role, a `users` table, Argon2id password hashing with a password policy, plain-SQL migrations with a one-shot compose runner, a `/ready` check for Postgres, and a reviewer CLI. No login, sessions or UI (M4.1b/c), no Python change.

Decisions:

- **Same server, separate database and role.** One more Postgres would double the operations; a separate database and a role that owns only it gives the gateway its own data without a second server. The role is `NOSUPERUSER NOCREATEDB NOCREATEROLE`, PUBLIC's default CONNECT right is withdrawn from `gateway` and from every other database, and the role's own rights on other databases are revoked, so the gateway role cannot read Python's tables. **The reverse does not hold:** Python's role is the image's bootstrap superuser (`POSTGRES_USER`), which can reach everything; fixing that means a least-privilege role for Python, a Python-side change out of scope here.
- **One SQL file for both ways in.** `db/gateway-db.sql` is idempotent (`\gexec` creates the role and database only if missing, `ALTER ROLE` re-applies the password every run) and reads the password with `\getenv`, so it never appears in a process's arguments. The init script (fresh volume) and `scripts/create_gateway_db.sh` (existing volume) both run it. **Bug found by testing against a real Postgres:** with `GATEWAY_DB_PASSWORD` set but empty, `\getenv` defines an empty variable and Postgres treats an empty password as "no password", so a rerun would have wiped the role's password. The SQL now refuses an empty or unset password with a real error (exit code 3), not only the shell wrappers.
- **Where `GATEWAY_DB_PASSWORD` lives: the root `.env`.** The db service needs it, compose can only interpolate from the root `.env`, and giving the db service `env_file: gateway/.env` would hand it the client hashes and the review key. Cost: the Python app also receives it (its `env_file` is the whole root `.env`), and it cannot be listed in `.env.example` (a Python test requires every name there to be a Python setting). The password therefore exists twice, in the root `.env` and inside `GATEWAY_DATABASE_URL` in `gateway/.env`; they must match.
- **The db service now has a healthcheck over TCP** (`pg_isready -h 127.0.0.1`). The postgres image's init phase runs a temporary server that listens only on the unix socket, so a socket check would report healthy before the init scripts finished and `gateway-migrate` could race them.
- **`pg` with plain SQL, no ORM; plain numbered SQL migrations.** The runner (`src/database/migrate.ts`) is about 100 lines: advisory lock, a `schema_migrations` table with SHA-256 checksums, one transaction per file, refusal on a changed or missing applied file or an out-of-order new one. Forward-only. **Verified against a real Postgres** that two and five concurrent runners apply a file exactly once, and that disabling the lock or the checksum comparison makes tests fail.
- **A one-shot `gateway-migrate` service, and the gateway does not migrate.** Compose orders it (`service_completed_successfully`), so a failed migration stops the gateway from starting rather than letting it serve against the wrong schema. It loads all of `gateway/.env` (compose cannot pick one variable from an env file); it is the same image and the secrets are the gateway's own.
- **Argon2id by `@node-rs/argon2` 2.2.2** (prebuilt binaries, no node-gyp), verified to install and run inside the `node:24-slim` image (glibc, x86_64). Parameters in one constants file: 19456 KiB, 2 passes, 1 lane. Measured on this machine, inside the image: hash median about 51 ms (min 39 ms; the first call after start was about 420 ms), verify median about 25 ms. `Algorithm` is a `const enum` in the package's typings, which `isolatedModules` cannot use, so its numeric value is used with a comment. `needsRehash` uses the library's `parseOptions` on the PHC string.
- **Passwords are NFC-normalized for hashing and checking alike,** so the same password typed with composed or decomposed accents works either way and cannot be used to get past the 128-character cap. `verify` returns false for a malformed hash and for an over-long password without hashing it, and never throws. The over-long shortcut applies equally to known and unknown accounts, so it reveals nothing.
- **A precomputed dummy hash** (a real Argon2id hash of a discarded random password) is exposed for M4.1b's "unknown email" path, and a test fails if the parameters change without regenerating it, because a dummy with different parameters would cost a different time.
- **Password policy** is length (12 to 128 characters, counted as characters after NFC), not the email or its local part, and a short blocklist (20 entries). No composition rules, as NIST advises. The blocklist is tiny on purpose; it stops the worst, not a determined guess.
- **The email rule is enforced twice:** the application trims and lowercases, and a CHECK constraint makes the database refuse anything else, so uniqueness really is case-insensitive even for a future code path that forgets.
- **The reviewer CLI is compiled TypeScript** (`src/scripts/reviewers.ts` becomes `dist/scripts/reviewers.js`), not a stripped-types script like the key tool. **Deviation from the task text** (which said `gateway/scripts/reviewers.ts`): the production image holds only `dist`, and the main build compiles only `src`, so a file under `scripts/` would not exist in the container. Passwords come from a no-echo prompt asked twice, or one line from a pipe; there is no `--password` option. Verified through a real pseudo-terminal as well as through pipes: typed characters are never echoed.
- **`/ready` gained `postgres`** (a `SELECT 1` with the same 1.5 s timeout, reasons from a fixed vocabulary including `authentication failed` and `database not found`). `/health` still touches nothing.
- **Pool:** max 10, 2 s connect timeout, 5 s statement timeout, lazy connect (the app starts with the database down), an `error` listener (an idle-connection error would otherwise crash the process), and `pool.end()` bounded to 2 s at shutdown (the Redis worker taught us that an unbounded close can hang `app.close()`).
- **The passthrough log line.** The task reported `client=opsroute="GET /tickets"`. I could not reproduce it: the code has always had a space, and Nest's logger prints it correctly (checked on its real stdout output). An exact-format test through the real logger now pins it. If the missing space was seen in a terminal, it may have been colour-code rendering.

Testing notes: real-Postgres tests live in `test/database.pg.e2e-spec.ts` and run only with `GATEWAY_TEST_DATABASE_URL` (a database whose name ends in `_test`; the spec drops its public schema). They were run against a throwaway Postgres container, not your compose database.

Open after this step: login, sessions and the UI (M4.1b/c); Python's superuser role; the shared server; no down-migrations; accounts have no self-service password change.

## Reviewer login: sessions, cookies and the Origin check (M4.1b)

What was built: `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`; sessions in Redis; a unified principal for API-key clients and logged-in reviewers; failed-login limits; session revocation from the CLI. No UI, no sign-up, no Python change (recording `reviewed_by` is M4.1c), no CORS.

Decisions:

- **Server-side sessions, not JWTs.** A session can be ended at once (logout, disable, password change) because the server holds the state; a JWT stays valid until it expires unless a blocklist is added, which is a session store in disguise. The cost is one Redis read and one Postgres primary-key read per request, which the per-request user check needs anyway. No `express-session`, no `passport`: the logic is small (about 250 lines across `src/sessions/`) and every line of it is tested; a framework would hide the parts that matter (what is stored, when it is written). The `cookie` package (2.0.1, exact pin, five months old) parses and serializes the cookie; `cookie-parser` was not added because only one cookie is ever read.
- **The token is hashed in Redis.** The cookie holds 32 random bytes; Redis holds the session under `session:<SHA-256(token)>`. A copy of Redis (a backup, a dump, a leaked snapshot) contains nothing usable as a cookie. Verified against a real Redis: no key or value holds a raw token or a raw email. Plain SHA-256 is right here because the token has 256 bits of entropy (there is nothing to brute-force), the same reasoning as the API keys.
- **Every request loads the user from Postgres** and refuses (and deletes) the session if the user is gone, disabled, or `password_changed_at` is later than the session's `created_at`. This, not the CLI, is the guarantee. CLI revocation (`user_sessions:<id>`) is only clean-up and may fail: tests prove a disabled user and a changed password are refused with revocation skipped. Cost: one indexed query per cookie request. A comparison of the database's `password_changed_at` with the gateway's `created_at` assumes the two clocks agree (same host in compose). If the database clock ran ahead, a login straight after a password change could be refused once; behind, a session created just before a change could survive until the next minute-granularity check. Not guarded against.
- **Lifetimes.** Idle timeout (60 min) and absolute lifetime (8 h); the Redis TTL is `min(idle, absolute remaining)` rounded up. Use slides the idle timer, but the write happens at most once a minute per session, so a busy page does not turn every request into a Redis write. Consequence: the idle timeout is measured from the last write, up to a minute before the last use. The service also checks the absolute lifetime itself, not only through the TTL.
- **Login always creates a new session** and deletes the session the request carried, so a token planted before login (session fixation) never becomes the logged-in one. Creating or deleting a session and updating the user's index is one Lua script each, so the two keys never disagree.
- **One guard, two callers.** If an `Authorization` header is present only the API key is considered (a bad key with a good cookie is 401, never a fallback); otherwise the cookie. A user is a `reviewer`, with exactly what a reviewer client has. The principal carries a namespaced `id` (`client:<name>` / `user:<uuid>`) used for rate-limit buckets and idempotency keys, so a user and a client can never collide.
- **How existing jobs stay compatible (the migration-free choice).** Jobs hold their owner in `data.client` as the bare client name. Rather than rewrite them, the principal has a separate `ownerId`: for a client it is the bare name (exactly what is stored today), for a user it is `user:<uuid>`. They cannot collide because client names cannot contain `:`. So no job is touched, a submitter still sees its old jobs, and a user-owned job is a 404 to every submitter. The things that are only ever transient did change to the namespaced id: rate-limit counters (`rl:client:<name>`, `rl:user:<uuid>`; 60-second windows) and idempotency keys (`idem:client:<name>:<key>`, `idem:user:<uuid>:<key>`; 24 hours). **Effect: an Idempotency-Key used within 24 hours before the upgrade no longer matches, so a retry in that window can create one duplicate job.** A bare `idem:<client>:<key>` format was rejected because a client named `user` could then collide with a user's key.
- **Cookie:** `tiq_session`, `HttpOnly`, `SameSite=Strict`, `Path=/`, `Max-Age` = the absolute lifetime, no `Domain` (host-only). `Secure` follows `COOKIE_SECURE`, which defaults to **true** (a missing or mistyped setting fails safe; only the words `true`/`false` are accepted). Local plain-http development needs `false` (browsers drop `Secure` cookies from `http://`); production must be `true`, which M6 (HTTPS) enforces. Logout clears the cookie with identical attributes.
- **Origin check on top of SameSite.** `SameSite=Strict` already stops cross-site cookie sends in current browsers; the exact-match `Origin` check is defence in depth for a browser that handles it badly, for same-site-but-different-origin pages and for odd proxies. Applied to login, logout and any cookie-authenticated write; API-key requests are exempt (no cookie, so no CSRF). A missing `Origin` is refused. **No CORS was added:** M4.3 serves the UI same-origin (a Vite dev proxy locally, the same host in production), so the browser never makes a cross-origin call. If that changes, add CORS then, deliberately.
- **Login protection.** Unknown email: verify against the precomputed dummy hash. Disabled user: verify fully, then refuse. All three failures return the same bytes, and the work done is the same (a unit and an e2e test check that `verify` is called on every path). Limits are checked **before** hashing, so a limited caller costs no Argon2 work; only failures count; a success clears the email's counter; the per-email key is the SHA-256 of the normalized email. A limited attempt is not counted again (a flood cannot extend its own lockout). Counting is atomic (Lua `INCR`); the check and the count are two steps, so a burst of concurrent attempts can overshoot the maximum by about the concurrency.
- **Known trade-off, not solved:** failing on someone's email locks that email out for one window (5 failures per 15 minutes by default), even for the real owner. The alternative is not limiting per email, which allows password guessing. Per-IP limiting does not help against a distributed attacker.
- **`TRUST_PROXY`** (default false) turns on Express `trust proxy`. With it off, the client IP is the socket address, so a caller cannot choose its own IP with a header. With it on, any `X-Forwarded-For` is believed, which is only safe behind a proxy that sets it itself; M6 should narrow this to a hop count or address range.
- **Rehash on login:** if the stored hash has old Argon2 parameters, it is replaced after a successful login with `rehashPassword`, which deliberately does **not** touch `password_changed_at` (that would log the user out everywhere) and only applies if the hash is still the one that was read (a concurrent password change is never overwritten).
- **Logging:** `login outcome=... reason=... user=<id> ip=...`. The submitted email, the password, the cookie, the token and its hash are never logged (people type passwords into the email box). Tests feed distinctive values through every path and search the logs.
- **The CLI** (`set-password`, `disable`) deletes the user's sessions through `user_sessions:<id>` and prints how many. If Redis is unreachable (or `REDIS_URL` is unset) it still succeeds on the database change and prints a warning, relying on the per-request check.
- **Error bodies:** the `/auth/*` endpoints and the guard's 401/403 on `/auth/*` use `message` (a browser client reads it); every other route keeps `detail` as before. The 401 for a request with no credentials on other routes still says "Missing or invalid API key" (existing contract).
- **Test timeout:** the unit config's `testTimeout` is 30 s: the Argon2 tests really hash (about 40 ms each, several threads) and timed out at the 5 s default when the whole suite ran in parallel.

Remaining gaps: reviews do not yet record who made them (M4.1c); no UI (M4.3); no password reset by email, no multi-factor authentication, no "remember me", no self-service password change; sessions are not listed or individually revocable by the user; the email lockout trade-off above; the clock assumption above; Redis is a single instance (a lost Redis logs everyone out, which fails safe); `TRUST_PROXY` is all-or-nothing.

## Who reviewed each ticket, and the login limiter fix (M4.1c)

What was built: Python records `reviewed_by_id` and `reviewed_by_name` with every review; the review request requires a `reviewer`; ticket reads return `reviewed_by`; the gateway derives `reviewer` from the authenticated principal; and the login limiter counts attempts first. No UI, no email, no change to who may review.

- **How the Python columns were added: Alembic, the repo's existing mechanism.** Schema is owned by Alembic and applied by `run_migrations()` at every startup (not by `ALTER TABLE` in `store.py`), so the change is migration `0003_reviewed_by.py`. It uses `ADD COLUMN IF NOT EXISTS` (and `DROP CONSTRAINT IF EXISTS` before adding the check), so it also survives a partly applied earlier attempt, and Alembic's version table makes a normal second startup do nothing. A CHECK keeps the pair together (both set or both NULL), so a one-sided write is refused by the database. No new migration framework. Rows reviewed before this keep NULL in both columns and read back as `reviewed_by: null`: their author was never recorded and is not guessed.
- **The author is written by the same UPDATE as the decision.** `record_review` is one statement with `status = 'pending_review'` in its WHERE clause, now also setting the two columns, so a review can never be saved without its author and a second review (409) matches no row and cannot overwrite the first reviewer. A test fails if the author is dropped from the write (the CHECK fires).
- **The name is a snapshot.** If a reviewer is renamed later, tickets they already reviewed keep the old name; the id is the stable identity. Cost: a name can differ between old and new reviews of the same person.
- **Why `reviewer` travels in the request body.** Names are any Unicode ("Ọbiọma Ụzọ") and HTTP headers are Latin-1-safe at best: a non-ASCII name in a header is mangled or refused by proxies and libraries. A JSON body carries Unicode exactly. A test sends such a name from the gateway and reads it back from Postgres.
- **Why Python can trust it.** `POST /tickets/{id}/review` already requires the service review key, which only the gateway holds. The gateway sets `reviewer` from what it authenticated (a user's session, or an API key's client) and never from the client's own body, which the existing strict schema rejects (a test sends `reviewer`, `reviewed_by`, `null`, a string, an empty object: all 400, Python never called). So `reviewed_by` means "who the gateway authenticated". **It is only as strong as the key:** anyone who holds `TRIAGE_REVIEW_API_KEY` can name any reviewer. Python validates the shape anyway (id `user:<uuid>` or `client:<name>`, name 1 to 100 characters after trimming) and answers 422 otherwise; the endpoint says so in a code comment.
- **`ReviewDecision` is unchanged on purpose.** It is what the graph resumes with (and is stored in graph state), and many tests build it. The endpoint takes a `ReviewRequest` (a `ReviewDecision` plus `reviewer`), passes the decision part to the graph and the reviewer only to `record_review`. The graph never sees reviewers.
- **The gateway checks `reviewed_by` in Python's answers** (a loose schema: only `reviewed_by` is looked at, and it may be an object, `null` or missing, so an older Python still works). A malformed one on a successful ticket answer becomes a 502 rather than being passed on. Error answers (404, 409, 422) are not checked.
- **The log line adds `reviewer=<namespaced id>`** for reviews only, never the name or the email. (For a user the `client=` label already was the namespaced id.)

The login limiter fix (found in the M4.1b review):

- **The flaw:** the limiter read the failure count, then, after the password check, incremented it. Between the two steps a burst of concurrent attempts all saw the old count, so about as many extra attempts as there were concurrent requests got through to Argon2.
- **The fix:** one Lua script INCRs the IP key and the email key (starting each expiry when the key is new) and returns both counts and TTLs; the verdict comes from that count. With a maximum of 5, attempts 1 to 5 proceed and every later one is refused with `Retry-After` and no Argon2 work. Verified against real Redis: 50 concurrent wrong-password logins for one email gave exactly 5 password checks and 45 `429`s, and a non-atomic variant made the test fail.
- **Counters stay meaningful:** a refused attempt is counted but cannot extend the window (the expiry is only set when a key is new). A successful login deletes the email key and decrements the IP key (never below 0) in one script, so at rest the counters count failures: many successful logins never limit anyone. Because a success resets the email counter, a stream of correct-password logins can exceed 5 over time; that is intended (the legitimate user is not throttled), and it is not a way to guess passwords.
- **Trade-offs unchanged:** the email lockout (anyone can burn someone's 5 attempts and block them for one window) and the IP caveat (`TRUST_PROXY`) still apply. A crash between counting an attempt and a successful login's give-back leaves the IP counter one higher until the window ends.

Testing notes:

- **Tests no longer depend on a local `gateway/.env`.** The config loader reads `gateway/.env` when present, and a developer's real file (for example `COOKIE_SECURE=false`) leaked into the e2e tests and failed the cookie assertions. `stubAuthEnv` now sets every login and session setting explicitly. (I never read or printed that file; the failure showed in the test output.)
- **A real cross-system check:** the real Python app (against a throwaway Postgres, so its startup migration ran) behind the real gateway image, driven with curl: Python accepted the gateway's body (409 for a row with no paused run and 404 for an unknown ticket, never 422), reads showed `reviewed_by: null`, a body with its own `reviewer` got 400, and the gateway log held no name or email. A reviewed ticket was not produced there because that needs a paused graph (model calls); that path is covered by the real-Postgres tests with faked model calls.

Remaining gaps: `reviewed_by` trust rests on the shared key; reviews before M4.1c have no author; no UI (M4.3); no reply delivery (M4.4); per-person review keys are not planned (the reviewer travels in the body).

## The public ticket form (M4.2)

What was built: `POST /public/tickets` (no login, no key), a gateway-made ticket reference for every ticket, and customer name and email stored for reviewers. No UI (M4.3c), no email (M4.4).

- **The design is about money, not about the form.** Anyone on the internet can call it and each accepted ticket costs paid model calls, so each protection has one job and the order is cheapest first: replay, honeypot, per-IP limit, Turnstile, daily cap, queue.
- **Why the daily cap comes after Turnstile.** If the cap were counted first, a bot with no valid token could send 200 junk requests and use up the day's cap, locking real customers out: the cap would be a denial-of-service switch for attackers. After Turnstile, only a request that passed the bot check can take a slot. The cost: Turnstile is called for every request that passes the IP limit, so the IP limit is what protects the Turnstile call volume.
- **Turnstile fails closed.** If Cloudflare is unreachable, times out (5 s) or answers 5xx, the visitor gets a 503, not a free pass. Protecting the spend beats availability here; the daily cap would still bound the damage of failing open, but an attacker could then trigger Cloudflare errors cheaply. A 503 is what the form shows as "try again in a moment". If our own secret is refused (`invalid-input-secret`) that is also a 503 (a misconfiguration is not the visitor's fault) and is logged as an error without the secret.
- **Replay before anything that costs.** The Idempotency-Key is looked at first with one Redis read. A completed request with the same message returns its original reference and uses no limit slot, no Turnstile call and no cap slot. The fingerprint leaves out the Turnstile token and the honeypot, because a retry has a new or already-spent token and must not become a conflict or a 403. Same key with a different message is 422, the same as `POST /tickets` (your brief said 409 "as today", but today it is 422).
- **A cap slot is only for a queued ticket.** It is given back if the enqueue fails or if two identical requests raced and this one lost. If the give-back itself fails the slot is lost until the day ends, which errs on the side of spending less.
- **Honeypot.** A filled `website` field gets a normal-looking 202 with a random reference that points at nothing, so a bot learns nothing. It counts toward the IP limit but takes no cap slot and no Turnstile call. A human whose browser autofills the hidden field loses their message silently: the field is hidden from people (M4.3c must hide it properly, not with `type=hidden`, which autofill ignores).
- **Origin is not a security control here.** The check turns away other websites' browsers early, nothing more: a script can send any Origin. The limits, Turnstile and the cap are what protect the spend. The IP is `request.ip`, so behind a proxy `TRUST_PROXY=true` is required, otherwise everyone shares the proxy's address and one limit. An IPv6 user can rotate within a /64; the daily cap bounds that.
- **Name and email stay out of the model.** They are stored (Postgres, and in the Redis job until it is removed) and shown to reviewers, but the graph is run with a copy of the ticket that has them removed, so they are in no prompt, no graph state and no checkpoint (a test dumps the checkpoint tables and looks). Never logged either: the log line holds the outcome, the reference, the IP and Turnstile's error codes.
- **The reference moved to the gateway, for all tickets.** The customer needs the reference in the 202, before Python has seen the ticket. The format is Python's exactly (31 characters, 6 places, no `0 O 1 I L`) and Python still generates one when none is supplied. A supplied reference is never changed: if it already belongs to another ticket Python answers 409 with the code `reference_conflict`, the worker dead-letters the job and logs an ERROR (the customer already holds that reference, and a retry cannot fix it). Collision odds: about n squared over 1.8 billion for n tickets: 1 in 2,000 at 1,000 tickets, about 1 in 18 at 10,000 tickets, so the reference length should grow before the volume does. A replay of the same ticket id with the same reference stays idempotent.
- **Old idempotency keys** (stored before this change, 24 hours) carry no reference, so a replay of one of those through `POST /tickets` answers without a `reference` field.
- **Reserved client name.** `public-form` is refused in `GATEWAY_CLIENTS`: public tickets are owned by that built-in name, and its idempotency namespace is `client:public-form`, so a real client can never share it.
- **Body limit.** 16 KB on `/public` (a 5000-character message of non-ASCII text is about 5 KB of text, 15 KB in the worst JSON escaping, still inside), 100 KB elsewhere.

Testing notes: the gateway's per-request settings in the e2e test are supplied through a ConfigService stand-in built by the real `validateEnv`, because the app reads its config once per test file. The counters' Lua scripts run against a real Redis (50 concurrent reservations against a cap of 5 reserve exactly 5).

Remaining gaps: the daily cap is global (one noisy day blocks everyone, by design); no CAPTCHA fallback; no per-email limit (one email can submit as often as the IP limit allows); no way yet to see a ticket's status as the customer (M4.4 sends replies).

## The web UI foundation and reference reservation (M4.3a)

- **Why the `/api` prefix and a proxy.** The gateway has no CORS on purpose, and its session cookie is `SameSite=Strict`. If the UI ran on its own origin and called the gateway on another, the browser would need CORS and the cookie would not be sent. So the browser only ever talks to one origin (`:5173` in development) and the UI's calls all start with `/api`; the dev server strips the prefix and forwards to the gateway. The prefix exists so the proxy can tell API calls from UI routes without a list of paths (UI routes never start with `/api`). It does not change `Origin`: the gateway's Origin check on cookie-authenticated writes sees the browser's real Origin, `http://localhost:5173`, which is in `ALLOWED_ORIGINS`. Production (M6) needs the same rule in Caddy (`handle_path /api/*` to the gateway, the rest to the static files). I checked the proxy by hand against a fake upstream: prefix removed, `Origin`, `Cookie`, `Set-Cookie` and `Retry-After` pass through.
- **Tailwind v4 with `@theme` tokens.** The mockup's colours live as CSS variables in one place (`src/index.css`): page `#F4F5F7`, accent `#2457D6`, hover `#1A3FA0`. Utility classes use the tokens, so a colour change is one edit. A test computes the WCAG contrast of every text/background pair from the CSS and fails below 4.5:1 (the accent on white is about 6:1).
- **No session in browser storage.** The only credential is the `HttpOnly` cookie, which scripts cannot read. TanStack Query's in-memory cache holds the user for the page's life and is cleared on logout and when a call answers 401. A 401 from the login call or the "who am I" probe is an ordinary answer (logged out), not "session ended".
- **Session-ended handling is global.** The API client calls a handler on any 401 from a normal call; the app registers it to clear the cache and go to `/login` with the message. A failed logout (network) does not pretend the session ended: it says so and stays.
- **Messages never show server text.** Errors are typed (`Unauthorized`, `RateLimited` with `Retry-After`, `Forbidden`, `ServerError`, `NetworkError`) and the page words them. The 429 message rounds the wait up to whole minutes ("Try again in 2 minutes" for 61 seconds).
- **After a login the user is re-checked, not trusted.** `/auth/me` is cached for 30 s and refetched when the window regains focus; an expired session found that way sends the user to `/login` without the "session ended" notice (a limitation: only calls that answer 401 show it).
- **Reference reservation.** The gateway makes the reference at accept time and tells the customer straight away, so it must be unique before Python ever sees it. Each reference is inserted into `ticket_references` (`ON CONFLICT DO NOTHING RETURNING`, up to 5 tries, then 503 and an ERROR log). With an Idempotency-Key the reservation happens only after the key is claimed: a replay reuses the stored reference (a pending claim stores the first candidate; if a later candidate had to be used, the stored value is replaced under a compare-and-set on the job id). Honeypot references are random and never reserved. A reference reserved for a ticket that then failed to queue is simply burned (rows are never released: 887 million possible references, so waste is harmless). **Pre-existing Python-generated references are not in the table** (they are dummy data, accepted): a gateway reference could in theory equal one of them, and Python's unique constraint plus the 409 `reference_conflict` (dead letter) remains as the backstop. Window: between the key being claimed and the reservation finishing, a concurrent replay would read the first candidate; this matters only when that candidate collided, so it is vanishingly rare.
- **Test notes.** MSW v3 renamed its option to `onUnhandledFrame`; the web tests run on jsdom with Node's fetch, so relative `/api` URLs are resolved against the page origin in `src/test/setup.ts`. After a logout the cache is cleared and `/auth/me` is asked again, so a test of logout must make its fake gateway forget the session when it answers the logout.

Not done in M4.3a: the queue list, the ticket page and review actions (M4.3b), the public form page and Turnstile widget (M4.3c), a Docker image and Caddy (M6).

## The review queue (M4.3b)

- **All customer and model text is plain text.** Subjects, messages, names, emails, review reasons, drafts, knowledge-base article text and reviewers' notes are only ever rendered as React text nodes (with `white-space: pre-wrap` so line breaks survive and long words wrap). There is no `dangerouslySetInnerHTML`, no markdown renderer and no auto-linking (an email address or URL in a message is not clickable). A customer can write `<img onerror=...>` or `<script>` and the reviewer sees those characters. The test checks that no element is created from such text. If a clickable link or formatting is ever wanted, it needs a sanitiser decision first, not a quick `innerHTML`.
- **Pagination is a keyset cursor, not an offset.** The list is newest first and tickets arrive all the time; with an offset a new ticket shifts every later page and one ticket would appear twice. The cursor is the `created_at` and `ticket_id` of the last ticket the client has, and the next page is the tickets strictly older than that pair (ties on `created_at` are broken by id, so none is skipped or repeated). The client builds it from the last item; "is there more" is "the page was full" (20), so a final page of exactly 20 costs one extra empty request. The cursor is validated in the gateway (shape and length) and again in Python (422).
- **Counts are separate from the list.** One `GROUP BY` returns every status (zeros filled in), so the tabs' numbers are cheap and exact, not "the length of what has been loaded". `GET /tickets/counts` is declared before `/tickets/:id` in both services; without that order "counts" is read as a ticket id.
- **Auto-advance.** After a review is saved the UI refreshes everything, asks for the newest pending tickets and opens the first one that is not the one just reviewed (not "the next one down the list": after a refresh the list order is the freshest information, and the newest pending ticket is also the one a customer has waited least for; simple, predictable, and it never lands on a ticket someone else has taken). If there is none it shows the empty state.
- **A 409 is information, not an error.** Two reviewers on one ticket is normal. The UI refetches the ticket and says "Already reviewed by <name>" (or "(reviewer unknown)"), then the panel turns into the reviewed view. The message sits outside the action buttons because the refresh removes them. The server's row lock means exactly one of two simultaneous reviews wins.
- **Refresh.** Lists, counts and the open ticket refetch every 30 seconds and when the window regains focus (TanStack Query's focus manager). There are no websockets. A ticket someone else reviewed while you were looking at it shows its reviewed state at the next refresh, or as a 409 when you act.
- **Tabs and the open ticket live in the URL** (`?tab=`, `?ticket=<reference>`), so a link can be shared and reload keeps the place. The detail is fetched by reference (the same route the gateway already offers), not by id.
- **Auto-handled tab.** Python has five statuses: `triaged` (the AI handled it, no review needed), `pending_review`, `approved`, `edited`, `rejected`. The first one gets its own tab (read-only: nothing to decide).
- **Not done:** no search box, no bulk actions, no assignment or locking while a reviewer reads a ticket (a second reviewer sees it until it is decided), no sorting by urgency (newest first only).

## The public form page and the queue refresh fix (M4.3c)

- **Why "/" is the form.** The form is the one page every customer sees and needs no account; reviewers are the few people who know to go to `/login`. So the root is the public page and the reviewer UI sits behind `/login` and `/queue`. The form route does not wrap anything in the auth gate and never calls `/api/auth/me` (a visitor would only get a 401 and a flash of loading). `/queue` still redirects a logged-out visitor to `/login`.
- **Turnstile sits behind a small interface** (`TurnstileLoader`: render a widget with token, expired and error callbacks; `reset`, `remove`). The real implementation loads Cloudflare's script on demand, only when the form page mounts (no other page ever contacts Cloudflare), with explicit rendering and action `public_ticket`. Tests inject a fake. Tokens are single-use, so after any failed submit the token is dropped (Send is disabled) and the widget is reset. An `expired` or `error` callback removes the token and says so. If the script cannot be loaded, Send stays disabled and the page says verification could not load; there is no fallback by design (no CAPTCHA fallback in this step).
- **Idempotency key.** One `crypto.randomUUID()` per form instance, reused when the same message is retried after a failure, so a request that did reach the gateway (but whose answer was lost) is not duplicated. The gateway refuses a key reused with different content (422), so if the visitor edits the text after a failure the form silently uses a new key. "Send another message" is a new form instance and so a new key. `randomUUID` needs a secure context: fine on localhost and on HTTPS (M6).
- **The gateway's 400 field errors** are mapped to fixed phrases per field (never a submitted value is echoed; the gateway does not send any). Errors for fields the form does not have (for example `turnstile_token`) become the general "Please check the form" message.
- **Honeypot.** A real input named `website`, positioned far off-screen (a bot that skips `display:none` fields still sees it), `aria-hidden`, `tabIndex=-1`, `autocomplete="off"`. The form sends whatever it holds; the gateway answers a filled one with a normal-looking 202 and queues nothing.
- **Production CSP.** The widget is an iframe and a script from `challenges.cloudflare.com`: a Content-Security-Policy must allow it for `script-src` and `frame-src`, or the form shows "Verification couldn't load". Added to the M6 checklist in ROADMAP.
- **The queue refresh bug.** Symptom: in a second window the ticket showed "Rejected" but the first window's list still said Pending and the counts were stale. Two causes. (1) TanStack Query refetches "on focus" only on `visibilitychange`, which does not fire when you click from one browser window to another that is still visible (side by side): so nothing refetched until a reload, apart from queries that mount fresh (opening a ticket fetches it). (2) Nothing connected the ticket's own status to the lists. Fixes: the focus manager now also listens to the window `focus` event; and `useTicket` refreshes the lists and counts whenever the ticket's status differs from what it was a moment ago OR from what a cached list says about it (so opening a ticket that someone else already decided corrects the list at once). This covers refetch (timer or focus), our own review and the 409 path, since all of them write the ticket's query data. The 409 path itself (click before any refetch: "Already reviewed by <name>") is unchanged and now tested to also update the list and the counts.
- **Not done:** no customer status page, no email (M4.4), no CAPTCHA fallback, no CSP or Caddy yet (M6).
